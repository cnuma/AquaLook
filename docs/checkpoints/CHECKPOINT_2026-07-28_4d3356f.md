## Fonctions validées

- récupération automatique après incident ;

### Notifications ntfy

Le transport HTTPS direct a été abandonné dans l’architecture actuelle après diagnostic :

```text
SSL - Memory allocation failed (-32512)
```

Mesures typiques :

- heap libre : environ 74 Ko ;
- plus grand bloc contigu : environ 39 Ko ;
- DNS et TCP opérationnels ;
- cause : fragmentation mémoire lors du handshake TLS.

Le transport validé est provisoirement :

```text
AquaLook -> HTTP port 80 -> ntfy.sh -> téléphone
```

Preuves observées :

```text
Notification: tcp host=ntfy.sh port=80 status=ok
Notification: reponse http=200
Notification: livree ... http=200
```

La réception sur téléphone est confirmée.

### Notifications par zone

Chaque zone possède deux options indépendantes :

- notifier au démarrage ;
- notifier à l’arrêt.

Validation utilisateur sur matériel réel :

- notification de démarrage reçue ;
- notification d’arrêt reçue ;
- aucun doublon observé ;
- déclenchement après transition physique réussie ;
- le shadow orchestrator ne produit pas d’événement ;
- une commande répétée vers le même état ne produit pas d’événement supplémentaire.

## Persistance

La configuration principale utilise le schéma NVS 2.

Le schéma ajoute un masque `uint8_t` par zone :

- bit 0 : début ;
- bit 1 : arrêt.

Migration depuis le schéma 1 :

1. validation stricte de la taille, du magic, du schéma, du payload et du CRC ;
2. copie des anciens champs ;
3. initialisation des masques à `0x00` ;
4. sauvegarde au schéma 2 ;
5. refus sans écrasement silencieux d’un bloc invalide.

Preuve de démarrage :

```text
Config: charge depuis NVS (schema 2)
```

Aucune perte de configuration n’a été observée.

## Journal Web

Route de diagnostic :

```text
GET /api/logs.txt
Content-Type: text/plain; charset=utf-8
```

La page Journal consomme directement la réponse texte.

Les ressources Web complètes sont servies depuis la carte SD. Après modification de `data/app.js` ou `data/logs.html`, recopier les fichiers dans :

```text
/www/app.js
/www/logs.html
```

`uploadfs` ne met pas à jour ces ressources SD.

## Règle de diagnostic Web

Avant toute correction de code concernant une interface vide ou incohérente :

1. vérifier `/api/status` et son JSON ;
2. vérifier directement `/app.js` ;
3. contrôler la version des fichiers `/www` sur SD ;
4. vérifier la cohérence avec le firmware ;
5. faire `Ctrl+F5` ;
6. tester en navigation privée ;
7. consulter la console JavaScript.

Cette règle évite de confondre cache ou ressources SD désynchronisées avec une régression du firmware.

## Invariants

1. ne pas réintroduire TLS directement sur le contrôleur principal sans nouvelle validation d’architecture mémoire ;
2. ne jamais libérer les sprites pour tenter de rendre TLS possible ;
3. préserver le tactile et le portail captif ;
4. préserver la récupération SD et la persistance des incidents ;
5. notifier uniquement après succès réel du backend ;
6. ne jamais bloquer l’arrosage sur une opération réseau ;
7. conserver les options de notification désactivées par défaut lors d’une migration ;
8. distinguer ressources LittleFS minimales et ressources Web SD ;
9. diagnostiquer firmware, SD et cache avant de modifier le front-end.

## Limites et dettes connues

- transport ntfy HTTP non chiffré ;
- ne pas utiliser de jeton sensible ;
- événements de zone en attente non persistés après reboot ;
- message `Preferences.cpp: nvs_open failed: NOT_FOUND` possible au premier démarrage du namespace ntfy ;
- avertissement `addApbChangeCallback(): duplicate` encore présent ;
- absence de partition core dump ;
- future passerelle TLS locale recommandée.
