Le commit `b0155f3` constitue l’état fonctionnel validé de la migration progressive des ressources Web vers la carte SD. Le commit documentaire créé par l’ajout du présent fichier devient la référence officielle de reprise pour un nouveau chat. Il ne modifie pas le firmware.

## 2. Objectif de l’étape

Déplacer progressivement hors de LittleFS les ressources statiques pouvant être servies depuis la carte SD, sans modifier le fonctionnement métier d’AquaLook et sans rendre le module dépendant de la présence de la carte.

Architecture retenue :

```text
Requête de ressource statique
        |
        +-- fichier présent dans SD:/www -> servi depuis la SD
        |
        +-- fichier absent ou SD absente -> fallback LittleFS
        |
        +-- absent des deux supports -> 404
```

L’objectif de cette première phase n’est pas encore de supprimer les ressources de `data/`, mais de valider une priorité SD sûre et réversible.

- carte SD montée avec succès en SPI logiciel ;
- type observé : `SDHC/SDXC` ;
- capacité observée : environ 30 436 Mo ;


### 3.2 Ressources Web servies depuis la SD

Les ressources statiques doivent être placées sur la carte dans :

```text
/www/index.html
/www/admin.html
/www/*.css
/www/*.js
/www/images/...
```

Le handler SD :

- ne traite que les requêtes `GET` et `HEAD` ;
- exclut les routes `/api/...` ;
- exclut `/setup` et `/logs` ;
- protège contre les chemins contenant `..` ou un antislash ;
- lit les fichiers en flux, sans charger la totalité d’une page en RAM ;
- ajoute l’en-tête de réponse suivant :

```text
X-AquaLook-Storage: SD
```

Validation navigateur effectuée sur `index.html` :

```text
HTTP/1.1 200 OK
content-type: text/html; charset=utf-8
transfer-encoding: chunked
X-AquaLook-Storage: SD
```

Conclusion : la chaîne complète montage SD -> ouverture -> lecture en flux -> réponse HTTP est validée.

### 3.3 Fallback LittleFS

Test effectué sans carte SD :

- AquaLook démarre normalement ;
- les pages Web restent accessibles ;
- les ressources sont servies depuis LittleFS ;
- aucune dépendance fonctionnelle obligatoire à la SD n’a été introduite.

Conclusion : le fallback LittleFS est validé.

## 5. Détail de l’implémentation

### 5.1 `StorageManager`

Ajout de :

```cpp
bool openRead(const char* path, FsFile& file);
```

Règles :

- le chemin doit commencer par `/` ;
- la SD doit être disponible ;
- un fichier déjà ouvert est refermé avant réutilisation ;
- l’accès à `SdFat` reste centralisé dans `StorageManager`.

### 5.2 `SdStaticHandler`

Nouveau handler dérivé de `AsyncWebHandler`.

Responsabilités :

- déterminer si la requête peut être servie depuis `/www` ;
- ouvrir le fichier via `StorageManager` ;
- diffuser le contenu avec `beginChunkedResponse()` ;
- attribuer le bon type MIME ;
- fermer automatiquement le fichier à la fin de la lecture ;
- laisser les handlers historiques traiter la requête si le fichier n’existe pas sur la SD.

### 5.3 `WebManager`

Ajout de :

```cpp
void registerSdStaticHandler(StorageManager* storage);
```

Le handler SD doit être enregistré avant `setupRoutes()` et avant `_server.begin()` afin de conserver la priorité SD.

### 5.4 `main.cpp`

Ajout unique dans l’ordre de démarrage Web :

```cpp
webMgr.registerSdStaticHandler(&storageMgr);
```

L’ordre important reste :

```text
ConfigManager / LittleFS
TFT
StorageManager / SD
Relais
Planning
WiFi
NTP
handler SD
routes Web
serveur Web
Météo
DisplayManager
```

### 5.5 Synchronisation des ressources

Script ajouté :

```text
tools/sync-sd-assets.ps1
```

Usage :

```powershell
.\tools\sync-sd-assets.ps1 -SdDrive E:
```

Nettoyage préalable optionnel :

```powershell
.\tools\sync-sd-assets.ps1 -SdDrive E: -Clean
```

Le script :

- copie récursivement `data/` vers `SD:\www\` ;
- préserve les sous-répertoires ;
- vérifie chaque fichier avec SHA-256 ;
- échoue si un fichier est absent ou différent ;
- évite de maintenir une seconde copie versionnée des ressources Web.

## 6. Invariants obligatoires à préserver

1. La SD reste optionnelle.
2. AquaLook doit rester administrable sans carte SD.
3. LittleFS reste le fallback tant que la migration n’est pas explicitement terminée.
4. Les routes `/api/...` ne doivent jamais être servies ou interceptées par le handler SD.
5. Le portail captif `/setup` reste intégré au firmware et indépendant de la SD et de LittleFS.
6. La page `/logs` reste intégrée au firmware.
7. `ConfigManager` reste propriétaire du montage LittleFS et de la persistance.
8. `StorageManager` reste propriétaire de l’accès `SdFat`.
9. Aucune lecture de fichier SD ne doit bloquer durablement la boucle principale.
10. Les fichiers Web sont lus en flux ; ne pas charger une page complète dans une `String` ou un buffer global.
11. Les ressources présentes sur la SD sont prioritaires sur leurs homologues LittleFS.
12. Un fichier absent de la SD doit continuer à pouvoir être servi par LittleFS.
13. Ne pas supprimer de ressource de `data/` avant validation explicite de sa présence et de son fonctionnement sur SD.
14. Ne pas modifier le moteur d’arrosage, les relais, le planning, la météo ou la configuration dans cette phase.
15. Toute suppression future dans `data/` exige une compilation et un `buildfs` réussis, plus un test avec et sans carte SD.

## 7. Anomalies et points ouverts

### 7.1 Callback APB SPI enregistré deux fois

Message observé au boot :

```text
[E][esp32-hal-cpu.c:110] addApbChangeCallback(): duplicate func=...
```

Trace associée :

```text
_on_apb_change
esp32-hal-spi.c:652
```

État :

- le module continue son démarrage ;
- la SD fonctionne en SPI logiciel ;
- le serveur Web, le WiFi, la météo et le NTP démarrent ;
- la cause probable se situe dans une double initialisation d’un périphérique SPI matériel, vraisemblablement écran/tactile ;
- ne pas attribuer ce message à la SD sans analyse ciblée.

À traiter séparément dans le prochain chat, sans mélanger avec la suppression des ressources LittleFS.

### 7.2 Compteur du splash

Message observé :

```text
[Splash] Etape 8/7 : Meteo
```

La SD ajoute une étape de démarrage, mais le total affiché reste fixé à 7.

Impact : uniquement visuel.

### 7.3 `logo.png` absent

Le navigateur a observé :

```text
404 GET /logo.png
```

Le fichier n’est trouvé ni sur la SD ni dans LittleFS, ou son chemin ne correspond pas à la référence HTML.

À vérifier avant toute suppression de ressources.

### 7.4 Performances

La lecture depuis la SD utilise le SPI logiciel. Le fonctionnement est validé, mais aucune mesure longue durée ou test de charge simultanée n’a encore été effectué.

## 8. Étape suivante recommandée

Ne pas supprimer immédiatement tout `data/`.

Procéder par lots contrôlés :

1. inventorier la taille et les références de chaque ressource Web ;
2. corriger le `404 /logo.png` ;
3. vérifier que CSS, JavaScript, images et pages secondaires portent aussi l’en-tête `X-AquaLook-Storage: SD` après désactivation du cache navigateur ;
4. conserver dans LittleFS une interface minimale de secours ;
5. retirer d’abord les ressources lourdes et non critiques ;
6. reconstruire LittleFS ;
7. tester avec SD présente ;
8. tester avec SD absente ;
9. vérifier les API, l’écran et le moteur d’arrosage ;
10. seulement ensuite réduire davantage le contenu de LittleFS.

Ordre de migration conseillé :

```text
images et icônes lourdes
pages HTML secondaires
CSS et JavaScript non indispensables au secours
page principale complète
```

À conserver temporairement dans LittleFS :

```text
une page minimale d’administration ou d’erreur
les éléments nécessaires au portail captif
les ressources nécessaires au diagnostic de secours
```

## 10. Critères de sortie de la migration

La migration Web vers SD ne pourra être considérée terminée que lorsque :

- toutes les ressources ciblées sont servies correctement depuis `/www` ;
- le cache navigateur a été neutralisé pendant les validations ;
- aucune ressource requise ne retourne 404 ;
- les routes API restent inchangées ;
- le module fonctionne avec la SD ;
- le module démarre et propose une interface minimale sans SD ;
- la compilation et le `buildfs` réussissent après réduction de `data/` ;
- aucun gonflement anormal, doublon HTML/CSS/JS ou modification hors périmètre n’est présent ;
- les tests matériels de planning, relais, météo, écran et redémarrage restent conformes.
