# Audit de sécurité — service Web `cloud/php-mutualized/` (AlwaysData)

- **Date :** 10 octobre 2026
- **Cible :** `https://aqualook.alwaysdata.net` (code source `cloud/php-mutualized/`)
- **Base auditée :** `main` au commit `68a2d0e`
- **Nature :** audit **statique** du code source, complété par un unique
  contrôle en direct à faible impact (voir constat n°1). Les tests actifs en
  ligne (fuzzing, scan d'endpoints) ne sont **pas** inclus : l'hébergement est
  mutualisé, ils doivent être scopés à part (intensité, fenêtre horaire) pour
  ne pas affecter les autres locataires ni enfreindre les CGU.
- **Documents liés :** `CYBERSECURITY_ARCHITECTURE.md`,
  `SECURITY_RISK_REGISTER.md`,
  `../architecture/ENROLEMENT_ET_SECURITE_LOCALE.md`.

## Périmètre couvert

Les 10 fichiers PHP (`index.php`, `db.php`, `auth.php`, `account.php`,
`enroll.php`, `mail.php`, `settings.php`, `env.php`, `cleanup.php`,
`router.php`), les deux pages `admin.html` / `app.html`, `.htaccess`,
`.env.example`, `.gitignore`. ~3 600 lignes.

## Verdict général

Code **remarquablement bien sécurisé**. Les risques classiques d'une
application Web sont tous traités correctement, et souvent commentés dans le
code. Aucune vulnérabilité exploitable n'a été trouvée. Les constats ci-dessous
sont de la défense en profondeur ou des points de configuration latents.

### Points vérifiés sains

| Domaine | Constat |
|---|---|
| Injection SQL | Aucune. Requêtes préparées partout ; `LIMIT`/`OFFSET`/`IN` n'utilisent que des entiers constants bornés, jamais de valeur externe. |
| Autorisation | Trois domaines (module/jeton, utilisateur/session, admin/jeton). Chaque route de l'espace utilisateur vérifie `user_owns_module()` avant toute lecture/écriture et renvoie 404 (pas 403) pour ne pas distinguer « pas à vous » de « inexistant ». Jeton admin comparé en temps constant (`hash_equals`). |
| Connexion | `password_verify()` même sur compte inexistant (anti-timing), message unique, plafonds par email + par IP, réponse « mot de passe oublié » identique et envoyée **avant** le mail. |
| Sessions | Jetons 256 bits, stockés en SHA-256, cookie `HttpOnly; Secure; SameSite=Strict`. |
| CSRF | Routes module/admin par jeton en en-tête `Authorization` (pas de cookie → pas de CSRF). Routes espace utilisateur par cookie `SameSite=Strict` + corps JSON strict. |
| Mail | CR/LF refusés (pas d'injection d'en-tête/commande SMTP), certificat TLS vérifié (`verify_peer`), mot de passe SMTP jamais relu par l'API. |
| Liens mot de passe | Dans le **fragment** d'URL (ne part pas au serveur, pas de fuite Referer/journaux), usage unique, hachés au repos, différenciés sans aider à deviner un jeton de 256 bits. |
| Empoisonnement Host | Évité : les liens mail viennent du paramètre `APP_BASE_URL`, jamais de l'en-tête `Host`. |
| XSS (client) | `esc()` couvre `& < > " '` et est appliqué à toutes les données non fiables (libellés, firmware, payloads de module, `issuedBy`, emails…). Couleur de zone validée en `#RRGGBB` strict avant un attribut `style`. Jeton de fragment parsé en `[0-9a-f]{64}` strict. Aucun `eval`, aucun sink dynamique, aucune redirection ouverte. |
| Secrets dans Git | `.env` ignoré ; `.env.example` ne contient que des `CHANGEME`. |

## Constats

### 1. `*.log` non bloqué par `.htaccess` — latent, non exploitable en l'état

Le `.htaccess` bloque `.env*`, `schema*.sql`, `router.php`, `cleanup.php`,
`*.md`, mais **aucun `*.log`**. Comme la réécriture vers `index.php` ne
s'applique qu'aux fichiers absents du disque (`RewriteCond !-f`), un journal
d'erreurs PHP écrit dans la racine web (`php.log`, `error.log`) serait servi
tel quel : chemins absolus du serveur, traces de pile, et tout contenu futur
d'`error_log()`.

**Contrôle en direct (10 oct. 2026) :** `GET /php.log` renvoie le JSON
`{"detail":"route inconnue"}` d'`index.php` → le fichier **n'existe pas** dans
la racine web de production (le log PHP d'AlwaysData est ailleurs). **Donc non
exploitable aujourd'hui.** Le `php.log` présent dans le dépôt local est un
artefact de développement (1er sept. 2026), non suivi par Git.

- **Gravité :** faible (latent).
- **Correctif (appliqué, branche `fix/cloud-securite-entetes-logs`) :** ajout
  de `.*\.log` à la liste `<FilesMatch>` du `.htaccess` ; ajout de `*.log` au
  `.gitignore`.

### 2. Aucun en-tête de sécurité HTTP — défense en profondeur

Pas de CSP, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`,
`Referrer-Policy`, HSTS. Le jeton admin vit en `sessionStorage` : un XSS
(aucun trouvé) deviendrait un vol de jeton, qu'une CSP limiterait. Le cadrage
(clickjacking) n'est pas bloqué.

- **Gravité :** faible.
- **Correctif (appliqué) :** bloc `<IfModule mod_headers.c>` dans `.htaccess`
  (`nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, HSTS
  host-only, et une CSP `default-src 'self'` compatible avec les scripts
  inline). Les pages ne chargeant aucune ressource externe, la CSP ne casse
  rien. `'unsafe-inline'` reste nécessaire tant que les scripts sont inline :
  étape suivante = les externaliser pour passer à une CSP par nonce/hash.

### 3. `.gitignore` ne couvrait que `.env` — hygiène

`php.log` était non suivi mais pas ignoré : un `git add -A` l'aurait committé
dans le dépôt **public**, révélant les chemins serveur.

- **Gravité :** informatif.
- **Correctif (appliqué) :** `*.log` ajouté au `.gitignore`.

## Risques assumés et documentés (pas des défauts)

- **Mot de passe SMTP en clair** dans `app_setting` : choix documenté
  (`settings.php`) ; une sauvegarde de base le contient. Le `.env` reste une
  alternative pour l'éviter.
- **Limitation par IP moins fine** derrière un frontal mutualisé
  (`REMOTE_ADDR` = frontal) : documenté ; la limite **par compte** reste exacte.
- **CSRF de l'espace utilisateur reposant uniquement sur `SameSite=Strict`**
  (sans jeton anti-CSRF) : correct sur un domaine dédié, choix explicite.

## Corrections de cette passe

- `cloud/php-mutualized/.htaccess` : `*.log` ajouté au blocage ; bloc
